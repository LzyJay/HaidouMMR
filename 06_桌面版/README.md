# 06_桌面版 — 双击即用，而且能直接操作

把 `03_看板\海斗隐藏分_数据看板.html` 装进一个原生窗口，
不用再开浏览器、不用敲命令行 —— **而且窗口顶部多了一条操作栏，
能直接重新算分、重建看板、打开数据目录。**

---

## 怎么用

双击包根目录里 **`HaidouMMR\HaidouMMR.exe`**（注意是个文件夹，别只拷走那个 exe）。

窗口打开后就是完整看板 —— 和浏览器里看到的是同一份 HTML、同一份数据，
桌面版只是换了个入口，不是第二套实现。

想确认 exe 有没有正确找到数据：

```
HaidouMMR\HaidouMMR.exe --check
```

它会打印数据根目录、看板路径，找不到会明确告诉你是哪一层缺了。
这个自检不加载 GUI，出问题时先用它定位。

想确认「按钮真能跑脚本」（不打开窗口、不进界面）：

```
HaidouMMR\HaidouMMR.exe --selftest-run _paths.py
HaidouMMR\HaidouMMR.exe --selftest-run _dash_rebuild.py
```

它走的是**和界面按钮完全同一个** `_run_script`，所以这里能跑通，
按钮就能跑通。排查「点了没反应」时先跑这个。

> ⚠️ 只支持 **Python** 脚本。`.js` 断言脚本（`_verify_*.js`）是给 Node 跑的，
> 用这个开关会报 `SyntaxError`（`runpy` 会把它当 Python 解析）——
> 那是预期行为，跑断言请用 `01_脚本\验证看板.bat`。

## 为什么只能开一个窗口

**重复双击 `HaidouMMR.exe` 不会再开第二个窗口** —— 程序会直接退出，
并尝试把已经开着的那个窗口叫到前台（最小化了也会拉回来）。
实在叫不到（窗口被隐藏等异常情况）才弹一个提示框。

### 为什么必须限制

不是「看着不整洁」，是**会写坏数据**。

两个实例各自点一次「重新计算」，就会有两个进程同时写同一批文件：

| 文件 | 谁在写 |
|---|---|
| `02_数据\海斗隐藏分_v2_本次估算.json` | 估算脚本 |
| `02_数据\海斗dashboard_data.json` | 看板重建脚本 |
| `03_看板\海斗隐藏分_数据看板.html` | 看板重建脚本 |

这三份是「读 → 改 → 整体覆写」，没有加锁。并发写的结果是**后写的那个赢**，
中途可能被读到半截内容 —— 轻则看板数据错乱，重则 HTML 被截断打不开。

### 怎么实现的

**命名互斥体**（`CreateMutexW`，名字 `HaidouMMR_SingleInstance_v1`），不是锁文件。

为什么不用锁文件：进程被任务管理器强杀、或者崩溃时，锁文件会**留在磁盘上**，
把程序永久挡在门外（就是所谓「僵尸锁」，用户还得手动去删文件）。
命名互斥体由**内核**管理 —— 进程一退出（无论怎么退）内核自动释放，永远不会留下僵尸锁。

锁机制本身出问题时会**放行**而不是拦住 —— 宁可多开一个，也不能打不开。

### 例外：诊断命令不受限制

`--check` 和 `--selftest-run` **不占锁、也不被锁拦**：

```
HaidouMMR\HaidouMMR.exe --check           # 随时能跑，哪怕窗口开着
```

这是故意的 —— 程序卡住或行为异常时，诊断通道必须随时可用。

代价是：**别在窗口正在「重新计算」的时候跑 `--selftest-run` 写数据的脚本**
（比如 `_dash_rebuild.py`），那还是会撞车。只读的（`_paths.py`）无所谓。

## 操作栏（桌面版独有）

窗口**右下角**有一个悬浮的 **「操作」** 按钮，点开就是操作面板
（再点一次收起）：

| 控件 | 作用 |
|---|---|
| **抓新局并重算**（主按钮） | 六步全自动：抓你的新对局（SGP，一次最多 100 局）→ 定向补抓新对手 → 重建全量评分 → **抓本人对局明细** → 估算 → 重建看板。**日常就点这个**，实测约 2 分钟 |
| **深度抓取（慢）** | 同上，但第一步换成完整 BFS 抓 300 人的战绩列表 —— 网络更全，但**十几分钟起**（见下节） |
| **■ 停止** | 只在任务跑的时候出现。点了不会立刻断 —— 脚本会在**安全点**（一轮抓完 / 一局算完 / 一个 epoch 算完）停下，通常 1~3 秒。见下面「中途停止」 |
| 进度条 / 剩余时间 | 面板打开时显示当前是第几步、这一步在做什么、还剩多久 |
| #hdMeta 状态行 | 一行字：`锚点局 09-27 18:54 · 隐藏分 1541`。没有估算结果时提示去点「抓新局并重算」 |
| 数据目录 | 用资源管理器打开 `02_数据\` |
| 操作 | 收起 / 展开面板，不挡看板 |

> 2026-09-21 面板精简：原来的「锚点分数」「截图后又打了」两个输入框和「只重算」「只重建看板」
> 两个按钮**已删掉** —— 锚点参数改成静默透传（从上次估算结果里读出来原样给后端，
> 后端按 gameId 自动跟随），你一个数都不用管。

### 中途停止（■ 停止）

点停止后桌面版写一个标志文件 `02_数据\_cancel.flag`，脚本在自己主循环的**安全点**
检查到它就抛 `SystemExit(3)` 退出（退出码 3 = 用户主动停止，与「失败」区分开，
界面显示「已停止」而不是「没有全部成功」）。

- **为什么不直接杀线程**：脚本是用 `runpy` 在**同一个进程**里跑的，没有独立解释器可以 kill；
  强行异步注入异常可能正好落在 `json.dump(...)` 中间 → 留下半个 JSON → 看板下次直接读不了。
  标志文件只在安全点生效，**绝不会写盘写到一半被打断**。
- **代价**：响应延迟 = 一个循环体的耗时（抓取侧约 1~3 秒，估算侧一个 epoch 几秒）。
  等待期间按钮变灰显示「停止中 …」。
- **停止后本次结果不保存**，数据保持上一次的完整状态。想继续就再点一次按钮。
- 新任务启动时会自动清掉残留的标志（否则新任务一启动就被脚本自己停掉）。

### 锚点为什么不用你填了

锚点分数是唯一没法自动获取的东西（它只存在于截图里），但它指向的是**某一局**。
所以程序记住那一局的 `gameId`（存在 `02_数据\_desktop_state.json`），
重抓数据之后让估算脚本自己去新轨迹里找同一局 —— **你一个数都不用填**。
只有换了新截图（分数变了）才需要填一次「截图后又打了」。

> ⚠️ 为什么不能靠「主人对局数增加了多少」去推：`--anchor-games-ago` 是相对
> **Elo 轨迹**数的，而轨迹只包含对手覆盖率 ≥ 7/9 的那部分对局。
> 新爬进来的局有些进不了轨迹，所以「对局数增量」≠「轨迹长度增量」，
> 拿它去推会**指到错误的局上，算出来的分是错的**。

### 分区位置

看板 Hero 区下面有一块**分区位置**，只显示**本地自算**的相对位置（同场圈分位 / 同局 10 人排名）。

> ⚠️ 曾经在这里接过外部界面的分位与段位，后来**整体移除了**：
> 那套刻度依赖平台方的全服分布，本地只有自己爬出来的一小块网络，算出来的「约前 X% / 段位」
> 精度是假的。与其给一个不可信的外部刻度，不如只显示能自证的东西。见 `00_使用说明.md` 铁律 54。
>
> ⚠️ **同局位置**模块只在**同一局 10 人**里比，mmr 的相对大小是可信的 —— 这是它还能留下的原因。

### 查别人的战绩（点玩家名）

看板 **逐局战绩 → 明细** 里，除当前视角之外的 9 个玩家名都是**可点的**（鼠标移上去会变金、
带虚线下划线）。点开是一个弹层：

| 区块 | 内容 | 需要联网吗 |
|---|---|---|
| TA 与你的同场记录 | TA 的隐藏分（主网络样本 <5 局则显示「样本不足」）、对局评分均值、**与你联手** N 局、**与你交手** M 局、同场 KDA | ✗ 纯前端 |
| 与你联手的记录（同队） | 每一局的：时间 / TA 英雄 / TA K-D-A / 伤害 / 承伤 / TA 的结果 / 你的结果 / **对局评分** | ✗ 纯前端 |
| 与你交手的记录（敌对） | 同上（分成两张表，一眼能看出哪几局是队友、哪几局是对手） | ✗ 纯前端 |
| 换个视角 | 「以 TA 为视角看整个看板」/「回到数据主人视角」 | ✗ 纯前端 |
| 抓取 TA 最近的对局 | 「抓取数据并估算隐藏分」按钮 → 实时抓 TA 最近 100 局 | ✓ 要客户端在运行 |

前四块的数据**完全来自看板自己**（`roster` 里每一局都是数据主人的局，按 puuid 反查即可），
所以用浏览器打开看板也能看 —— 只是最后那个按钮会**禁用**并提示「请用桌面版打开看板」
（浏览器里没有 `window.pywebview`，调不到本地接口）。

**「对局评分」和「隐藏分」是两回事**，别混：

| | 隐藏分（mmr） | 对局评分（comp） |
|---|---|---|
| 含义 | 全网络刻度上的**长期水平** | **那一局**该玩家自身表现换算的分（0~100） |
| 变化 | 跨局基本不变（一个快照） | 逐局变化 |
| 可比性 | 可和你自己的分直接比 | 同一局 10 人之间可比；跨局只能大致比 |
| 算在哪 | `player_elo.json` | `_dash_rebuild.py` 的 `_roster_player_comp()`（**v6** 曲线，分母取我方 5 人之和） |

所以弹层里逐局表那一列是**对局评分**（跨局不变的隐藏分放逐局表里没信息量），
隐藏分只在 KPI 区出现一次。

点「抓取数据并估算隐藏分」会跑 `01_脚本\_player_probe.py`（SGP 优先、LCU 回退，
和抓你自己的战绩**同一套通道**），实测 **2~4 秒**。结果会报**两条**分数，都给你：

- **主网络已有分**：TA 已经在围绕你的那套网络（`player_elo.json`）里有分（样本 ≥5 局）
  —— 这个最可靠；
- **本地走查分**：TA 不在主网络里时，拿 TA 最近这些局按时间序跑一次在线 Elo，
  对手的分直接取自主网络。⚠️ 对手分是**终值快照**而不是同时刻值，
  所以它和「主网络已有分」差个十几二十分是**正常的**（实测两名对手：差 10.6 / 23.8 分）。
  每局有分的对手平均不到 3 人时，这个数基本等于瞎猜 —— 界面会**标红**提醒。

> 查别人**不会**影响你自己的数据：结果只写进 `02_数据\_player_probe.json`（临时文件，可随时删）。
> 但如果你正在跑「抓新局并重算」，按钮会先拒绝并提示等一等 ——
> 两个任务同时跑会互相抢 `sys.argv` 和标准输出。

### 进度条和剩余时间是怎么算的

任务在**后台线程**里跑，界面每 0.5 秒轮询一次进度，所以跑起来不卡、也不会
「点了没反应」。进度来自两处：

| 来源 | 说明 |
|---|---|
| **脚本自己的输出**（优先） | 六步**全部**有真实标记：`已抓列表 k`、`[列表] k/N 人`、`[详情] k/N 局`、`[Elo] k/N 局`、`[Stats] k/N 局`、`[1/4]`…`[4/4]`、`[load]`→`聚合完成` |
| **估时兜底**（只有「压根没有标记」的步骤才用） | 按「已用时 ÷ 该步预期耗时」线性推进，**封顶 90%** |

⚠️ **有标记的步骤，标记没到之前进度条是 0，不会先用估时跑。**
看着像「卡了一下」，其实是在等脚本吐第一行能认的输出（通常 1~4 秒）。
为什么不先跑：估时是**上次实测值**，步骤一旦比上次慢，估时就会在第一个标记到达前
冲到 90%；等脚本的第一个标记（值往往小得多，比如 `种子局详情` 只有 50%）一到，
进度条就**往回退** —— 2026-09-21 实测就出现了 `0.0167 → 0.0093` 的倒退。
宁可开头停几秒，也不要倒退。

剩余时间按**实际速率**外推（`已用 ÷ 已完成比例`），早期样本太少时退到估时，
界面上再做一次平滑 —— 否则数字每 0.5 秒抖一次，看着像坏了。

每次跑完会把各步的**实测耗时**记进 `02_数据\_desktop_state.json`，
下次直接沿用，所以估时会越用越准（不是永远用出厂常数）。

> **估时不准不会导致误报完成。** 完成的唯一信号是脚本真的退出（退出码），
> 进度条永远不会因为时间到了就跳到 100%。
>
> 优先级是「**有真实标记就只认标记**」：某一步的估时再离谱，也不会盖过脚本
> 自己报的百分比。只有在一步完全没吐标记时才按估时线性推进，并**封顶 90%**。
> 这条是踩出来的 —— 补抓实测 9.9 秒 ~ 464 秒，估时取小值的话，
> 「脚本说才 5%」会被演成「快 90% 了」。

**操作栏只在桌面窗口里出现。** 用浏览器直接打开那份 HTML 时看不到它 ——
因为按钮靠 `window.pywebview` 判断环境，浏览器里没有这个对象，
所以工具栏不渲染，`验证看板.bat` 的 101+39+186 条断言也完全不受影响。

**重要**：桌面版跑脚本的方式是在**当前进程内**用 `runpy` 执行，
不是另起一个 `python.exe` —— 因为打包后的 exe 里没有独立的 Python 解释器。
所以 `01_脚本\` 会在打包时被复制进产物（onedir 下落在 `HaidouMMR\_internal\_scripts\`）。
数据仍然不打进 exe。

⚠️ **「改了要不要重新打包」分两种**（2026-09-21 实测更正）：

| 改了什么 | 要重新打包吗 | 怎么生效 |
|---|---|---|
| `01_脚本\*.py` | **不用** | onedir 下 `_internal\_scripts\` 是磁盘上的**散文件**，运行时直接读。拷过去即可：`cp 01_脚本/X.py HaidouMMR/_internal/_scripts/X.py`，然后 `sha256sum` 对一下两边 |
| `06_桌面版\app.py` | **必须** | 它被冻进 exe 本体，磁盘上改不动。跑 `build.bat`（约 1 分钟） |

（实测：只改 `_internal\_scripts\_hd_crawl.py` 就跑
`HaidouMMR.exe --selftest-run _hd_crawl.py --seed --players 0`，新日志立即出现，
不需要重新打包。）

## 为什么「抓新局」很快，而「深度抓取」要十几分钟

**瓶颈是 LCU 限流，加并发没用。**

本机实测（2026-09-21）：`_hd_crawl.py --players 300` 光**拉 300 人的战绩列表**
就花了 **532 秒** —— 约 0.56 请求/秒，`--workers 16` 完全帮不上忙。

所以两条路分工：

| 路径 | 第一步 | 实测耗时 | 什么时候用 |
|---|---|---|---|
| **抓新局并重算**（默认） | `--seed --players 0`，只处理你自己的对局（SGP 一次 100 局，遇旧即停） | 秒级 | 日常。刚打完几局想看分 |
| **深度抓取** | 完整 BFS 抓 300 人 | 9 分钟起 | 偶尔。想让对手实力估计更准 |

**为什么「抓新局」就够了**：你自己的对局本来就能一次抓回来（SGP 100 局/请求）；
真正缺的是**新对手**的实力数据 —— 那由 `_hd_backfill.py` 定向补抓解决
（它专门挑「在你最近 20 局里出现、但在网络里出现 <5 次」的对手去补抓 20 局）。
完整 BFS 是把整个网络再扩一圈，属于锦上添花，不是必需。

> `--players 0` 是合法的「只抓窗口、不跑 BFS」写法（`budget <= 0` 直接 break），
> 不是笔误。

### 点一次「抓新局并重算」，实际跑的 6 步

| # | 步骤 | 脚本 | 实测耗时（2026-09-21） | 要客户端 |
|---|---|---|---|---|
| 1 | 抓取最新对局 | `_hd_crawl.py --seed --players 0` | 2.9 ~ 5.4s | ✅ |
| 2 | 补抓新对手 | `_hd_backfill.py` | **9.9s ~ 464s** | ✅ |
| 3 | 重建全量玩家评分 | `_player_elo_build.py` | 2.6 ~ 3.2s | ❌ |
| 4 | **抓本人对局明细** | `_stats_crawl.py` | 11 ~ 25s | ✅ |
| 5 | 估算隐藏分 | `海斗隐藏分估算_v2.py` | 102 ~ 113s | ❌ |
| 6 | 重建看板 | `_dash_rebuild.py` | 1.5 ~ 1.7s | ❌ |

一次完整 `update`（数据已是最新时）实测 **129.8 秒**。

**第 1 步是增量的**：从战绩列表**最新往前翻，遇到已经抓过的局就停**，
只抓新打的那几局。日志里会明确写：

```
✓ SGP: TENCENT_HN1  https://hn1-k8s-sgp.lol.qq.com:21019  （一次最多 100 局）
  种子窗口[SGP]: 翻了 1 页 × 100 局，遇到已抓过的局就停
  增量对比: 已有 29384 局 → 这次新局 0 局（没有新打的）
```

**通道是 SGP（sona 插件用的那条），不是 LCU 本地窗口。** 一次请求 `count=100`
就能拿 100 局完整对局（实测 11.8 MB / 2.5s），而且**详情随响应一起回来**，
不用再逐局拉 —— 所以「攒了 60 局没跑」也能**一次全补回**（实测 60/60，3.0s，一个不漏）。

```
⚠ SGP 不可用（拿不到 accessToken），改用 LCU 本地窗口（约 21 局）
  种子窗口[LCU]: 翻了 1 页 × 20 局
```

SGP 挂了会自动回退到 LCU —— 那条路一页只给 20 局、本地只缓存 ~21 局
（2026-09-21 实测：09-14 19:36 → 09-21 19:28）。真落到回退路径上，
**攒超过 20 局就抓不全了**，第 2 步能从对手战绩里间接捞回一部分，但不保证全。
想确认走的是哪条通道，看日志里 `✓ SGP:` 还是 `⚠ SGP 不可用`。
（`--no-sgp` 可以强制走 LCU 回退路径，用来验证回退逻辑。）

**第 4 步不能省。** 看板的 9 项指标（伤害/承伤/经济/治疗占比…）全部来自
`_stats_crawl.py` 生成的 `my_stats.json` / `海斗roster.json`。漏掉它，
第 5 步会因为新抓的局没有 stats 直接 `KeyError` 失败。
（2026-09-21 就是漏了这一步才炸的，已在 `_dash_rebuild.py` 里加了
「缺 stats 只告警不崩」的保险。）

**第 2 步的耗时差异很大**：刚跑过再跑只要 ~10 秒；攒了两周（177 个新对手）
要 464 秒。这个差异没法用一个常数表达，所以估时会**用上次的实测值**，
且「有真实标记就只认标记」，估时偏了也不会让进度条说假话。

## 为什么没有黑窗口

打包时带了 `--windowed`（= `--noconsole`），exe 是 **GUI 子系统**，
双击不会再先弹一个命令行窗口。

不加这个参数的话 PyInstaller 默认打成 **Console 子系统**，
Windows 会给它分配一个黑窗口，双击时先闪（或一直挂着）一个命令行 —— 很难看。

**代价是没有控制台**，所以诊断命令的输出行为变了：

| 怎么跑 | `--check` / `--selftest-run` 的输出 |
|---|---|
| 从 cmd / PowerShell / 终端（含管道、重定向） | 照常打印 ✓ |
| 从没有控制台的地方（带参数的快捷方式、计划任务） | **弹一个消息框**把结果摆出来 |

第二条是兜底：`--windowed` 下 `sys.stdout` 可能是 `None`，
不处理的话命令跑完什么都不显示，用户完全不知道发生了什么。
`app.py` 里的 `_ensure_stdio()` 会先尝试接回父进程的控制台，
接不上才退到弹框。

同一个兜底也用在 GUI 启动失败时 —— 否则「双击没反应」这种问题根本没法排查。

## 为什么数据不打包进 exe

`02_数据\` 有 45 MB 左右，而且你每抓一次新数据它都会变。
数据打进 exe 的话，**每更新一次数据就得重新打包一次** —— 不合理。

所以 exe 只装「窗口 + 渲染」，数据留在包里，运行时现读。
好处是：**更新数据完全不用重新打包**。

exe 会自动向上探测含 `02_数据` 的目录，因此：

- exe 待在 `HaidouMMR\` 里（标准位置）✅
- 整个分享包整体挪到别的盘 ✅
- **单独把 `HaidouMMR.exe` 拷到桌面 ❌** —— 那样它找不到数据，会弹一个提示页。
  它依赖同目录下的 `_internal\`，**拷一个文件出来是不能用的**。

## 重新打包

双击 `build.bat`。它会：

1. 在 `06_桌面版\.venv-build\` 建独立 Python 环境（**不动你全局的 Python**）
2. 装 `pywebview` + `pyinstaller`
3. 先跑 `app.py --check` 预检，找不到看板就中止（不会打个坏包出来）
4. PyInstaller 打包，产物挪到包根 `HaidouMMR\`
5. 对产物再跑一次 `--check`，确认打出来的东西真能用

首次打包要下载依赖，约 4-6 分钟；之后约 1-2 分钟。

**如果 `build.bat` 出问题**，跳过它直接跑：

```
python build.py            # 完整打包（默认 onedir，启动快）
python build.py --onefile  # 打成单文件 exe（便携，但启动慢 6-8 倍）
python build.py --check    # 只查环境和预检，不打包
python build.py --clean    # 打包前先清掉中间产物
```

打包逻辑全在 `build.py` 里，bat 只是个「找到 Python 然后调它」的壳。

`.venv-build\` 可以随时整个删掉，下次打包会自动重建。

**重新打包时旧版本会挪到包根 `_stale\`**，不会被删 —— 确认新版正常后可以整个删掉。
（不直接删是因为受限环境里批量删 255 个文件会被安全策略拦下，
而且留一份旧版等于自带回滚路径。）

## 为什么默认 onedir 而不是单文件

本机实测（2026-09-20，用 `--check` 计时，走完整启动路径）：

| 打包方式 | 启动耗时 | 体积 |
|---|---|---|
| **onedir**（默认） | **1084–1133 ms** | 30.4 MB / 255 个文件 |
| onefile | 6411–8343 ms | 15.0 MB / 1 个文件 |
| 裸 Python 解释器（参考） | 1259–1380 ms | — |

单文件版每次启动都要把 15 MB 解压到 `%TEMP%`，然后杀软逐个文件扫一遍 ——
**慢 6–8 倍，全部耗在这一步上**，跟应用本身没关系（onedir 已经接近裸 Python 的速度）。

附带好处：onedir 不需要自解压，所以也没有 `%TEMP%\_MEI*` 残留泄漏
（单文件版被强杀时会漏 25 MB 左右，正常关窗口不会）。

代价：产物从一个文件变成一个文件夹。**要「拷到哪都能跑」的单文件版时，
用 `python build.py --onefile`。**

## 已知限制

- **杀软可能误报** —— PyInstaller 产物的通病，已加 `--noupx` 缓解。
  真被拦就把包根目录加进白名单。
- **`HaidouMMR.exe` 不能单独拷走** —— 它依赖同目录的 `_internal\`（265 个文件）。
  要单文件便携版就用 `python build.py --onefile` 重新打一个。
- **改了 `01_脚本\*.py` 不用重新打包** —— onedir 下 `_internal\_scripts\` 是磁盘上的散文件，
  运行时直接读。拷过去 + `sha256` 对一下即可（改完 `01_脚本` 记得同步，否则 exe 里跑的还是旧的）。
  只有改 `06_桌面版\app.py` 才必须重新打包 —— 它被冻进 exe 本体。
- **启动失败会弹一个消息框** —— `--windowed` 没有控制台，崩溃时 traceback 没地方去。
  所以 `app.py` 兜底弹框显示原因。看到这个框就是启动出问题了，把内容发我。
- **只能开一个窗口** —— 第二个实例会自己退出并叫醒第一个窗口。
  如果你在任务管理器里看到两个 `HaidouMMR.exe`，那是打包器残留或强杀后的僵尸，
  不是单实例锁失效；锁由内核持有，进程真死了一定会释放。
